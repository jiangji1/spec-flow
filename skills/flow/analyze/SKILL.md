# 需求分析 /analyze

收到需求后、动手前先完成本步骤。产出「需求理解 + 待确认问题清单」，经用户确认后才进入 /spec 或 /plan。

## 要做的事

1. **复述需求**：用自己的话把需求说一遍，列出输入、输出、触发条件。
2. **口径逐条标注证据等级**：
   - 【文档】接口文档/需求文档写明的 —— 直接照做，不标疑。
   - 【推断】从代码、类型或关联逻辑推出来的 —— 必须显式标注「推断」，等用户确认，禁止静默当事实。
   - 【实测】已跑过、抓包看到的 —— 注明怎么测到的。
3. **查关联但不动**：需求没提的关联点（即使看起来强相关）一律保持原样，只列为待确认。
4. **待确认问题清单**：能从代码/文档实证的先查；查不到的停下来问用户，不要猜。
5. **分流**：调用 spec-flow-go 按其决策树判断走全流程（/spec）还是轻通道（/patch），把判断结果和理由告诉用户。
6. **确定 feature**：全流程使用 kebab-case 标识，后续产物统一放入 `.spec-flow-workspace/<feature>/`；不擅自覆盖同名已有需求。

## 停止条件

待确认问题清空（用户逐条回复，或确认无异议）。全流程随后进入 /spec；/patch 不强制创建工作区。

## 红线

- 禁止静默推断后写入任何产物。
- 被追问来源时，如实分层交代：文档转录 / 推断 / 实测。
- 同一失败查询不重复发起；查不到就记录「查不到」。
