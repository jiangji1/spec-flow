# AI 代码审查 /review

对照 <skill-dir>/references/review-checklist.md，按五个维度审查本次改动。全流程需求将报告写入 `.spec-flow-workspace/<feature>/review.md`，格式使用 <skill-dir>/references/review-template.md；/patch 可只在回复中给快审结论。

## 五维

1. **正确性**：实现与 spec 口径逐条对齐；边界与异常路径覆盖；防重/时序结论核查过 await 边界。
2. **安全**：注入、XSS、敏感信息泄漏、越权入口。
3. **性能**：不必要的重复请求/渲染；能合并的循环；大列表处理。
4. **可维护性**：命名表意、无重复代码、改动面是否最小、有没有需求之外的东西混进来。
5. **测试覆盖**：验收标准每条有测试或验证步骤；删改过的测试说明理由。

## 动作

- 先锁定评审范围与需求背景来源；无对应 Spec 时用用户输入或 MR 说明作为依据，不编造正确性结论。
- 发现问题就地修复，并说明根因——不是只报不改。
- 有分歧或需要业务裁决的，列入待裁决项等用户决定，不要自作主张。
- 修复后重跑相关测试确认没引入新问题。
- 全流程通过 spec-flow-go 随附的验证器执行 `--stage review`；未实际执行成功时不得声称机器校验通过。

## 结论

- **PASS**：无未处理阻断项、无待裁决项。
- **PENDING**：有需要用户裁决或补充信息的事项。
- **REJECT**：有未修复且未获用户明确豁免的阻断项。
- 豁免必须记录问题、豁免人和理由；豁免后不得把原 finding 从报告中删除。

## 红线

- 禁止为过审而弱化测试或放宽断言。
- 审查结论要给出具体文件与行为依据，不空泛打分。
- 有阻断项时禁止写 PASS；有待裁决项时最多写 PENDING。
