# 技术方案 /plan

基于同目录已确认的 `spec.md`，按 <skill-dir>/references/plan-template.md 产出 `.spec-flow-workspace/<feature>/plan.md`。

## 要做的事

1. **技术方案**：方案概述与选择理由。选型首要标准：**AI 能否全程驱动**（纯代码、可命令行构建、AI 能读改全部产物的方案优先）；需要 GUI 手工步骤的方案要明确列出哪些步骤必须用户亲自做。
2. **改动清单**：文件级别的表格（文件、改动、理由）。
3. **改动最小化检查**：需求未提及的关联点是否全部保持原样？往公共配置/共享链路加东西时，是否限定了单据类型？不满足就先收窄。
4. **任务拆解**：垂直切片，每个 Task 写明依据来源、文件、步骤、验证方式和关联 AC；全部 AC 至少被一个 Task 覆盖。
5. **风险与回滚**：只列本次真实风险及缓解方式，说明改坏了怎么退，不凑固定数量。
6. **跨产物语义审查**：逐条确认 Task 的实际行为满足关联 AC，验证方式确实能证明 AC；检查是否引入 Spec 未定义的新功能、页面、依赖或接口，以及是否违反不改动范围。编号存在但行为冲突时不得通过。
7. **结构校验**：通过 spec-flow-go 随附的验证器执行 `--stage plan`；在 spec-flow 仓库也可运行 `node scripts/validate.mjs .spec-flow-workspace/<feature> --stage plan`。未实际执行成功时不得声称机器校验通过。

## 停止条件

语义审查与结构校验都通过，用户确认方案后才把 `status` 改为 `plan-confirmed` 并进入 /build。这是第二个、也是最后一个写码前的人工确认点。

## 红线

- 方案里出现「顺便重构/顺便优化」的字样，删掉——那是需求没提的东西。
- 数据库、共享缓存等持久层改动必须说明影响范围和是否可回滚。
