# 改动范围纪律

防止「顺手多改」和「静默扩大」的规则，全部来自实际被批评的案例。

## 核心规则

1. **需求只让改什么就只改什么**。需求未提及的关联点（即使看起来强相关）一律保持原样；不确定先问。
   - 案例：需求只要「同一 URL 发 2 次请求、请求头分别带不同品牌」，代理却把 URL 也改成随品牌切换——需求根本没提 URL。
2. **口径类改动先说方案再动手**：业务口径、联动规则、共享组件行为——先口述方案，等用户确认后动手。
3. **文档没说的不改**：往公共配置/共享链路加东西时，限定到具体单据类型，不做全局开关。
4. **接口文档是权威**：文档已写明的值域/语义直接照做，不标「待确认」；只有文档没写的才推断标疑。
5. **接口未就绪不写 mock**：用 dev 内联假数据，必须符合业务公式；路径造不出时加 localhost 后门并注明临时性。

## 自检清单（每次动手前过一遍）

- [ ] 改动清单里有没有需求没提的文件？
- [ ] 有没有「顺便」「顺手」类的改动？
- [ ] 动的是公共配置/共享组件吗？是的话有没有限定单据类型？
- [ ] 口径变了吗？变了的话方案说过了吗？
- [ ] 有没有把推断当成事实写进去？
